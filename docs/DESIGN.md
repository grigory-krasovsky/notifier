# Notifier — дизайн

Telegram-бот для напоминаний о событиях. Документ фиксирует согласованные бизнес-правила
и техническую модель; обновляется по мере развития проекта.

## Термины

- **Событие (event)** — серия уведомлений, созданная пользователем: название, расписание, настройки напоминаний.
- **Срабатывание (occurrence)** — изначальный акт уведомления по расписанию события.
- **Напоминание (reminder)** — повторный акт уведомления по срабатыванию, которое пользователь ещё не закрыл кнопкой «Готово».

## Бизнес-правила

1. **Две периодичности у события, независимые друг от друга:**
   - расписание срабатываний (однократно / каждые N минут / ежедневно в HH:MM / еженедельно по дням);
   - интервал напоминаний (без напоминаний / каждые N минут, пока срабатывание не закрыто).
   Обе задаются пресетами в диалоге, без cron.
2. **«Готово» закрывает срабатывание, не событие.** Отдельное действие «Завершить серию» переводит событие в FINISHED. Событие можно ставить на паузу (PAUSED) и возобновлять.
3. **Долг не копится.** Если пришло время нового срабатывания, а старое не закрыто — старое автоматически закрывается со статусом SUPERSEDED. У события не бывает двух открытых срабатываний (закреплено уникальным частичным индексом в БД).
4. **Рабочие часы** (по умолчанию 9:00–22:00, настраиваются per-user) ограничивают:
   - напоминания — всегда: вне рабочих часов откладываются до их начала;
   - интервальные срабатывания (EVERY_N_MINUTES) — тоже;
   - но **не** расписания с явным временем: DAILY/WEEKLY/ONCE на 03:00 срабатывают в 03:00 — пользователь сам так задал. Напоминания по такому срабатыванию начнутся уже в рабочие часы.
5. **Таймзона** запрашивается при онбординге (`/start`); Telegram её не передаёт. Локальное время расписаний хранится вместе с таймзоной пользователя (не как фиксированный UTC-момент) — так переживём перевод часов.
6. **Пропущенные уведомления** (бот лежал в момент срабатывания) — поведение пока не решено, вернёмся позже.

## Модель данных (PostgreSQL, Flyway: `src/main/resources/db/migration`)

- `app_user` — telegram_chat_id (uniq), timezone (IANA), work_start/work_end, created_at.
- `event` — user_id, name, status (DRAFT/ACTIVE/PAUSED/FINISHED; DRAFT = собирается визардом `/new`, планировщик и `/list` его не видят), schedule_type (ONCE/EVERY_N_MINUTES/DAILY/WEEKLY) + параметры (interval_minutes, time_of_day, days_of_week), first_fire_at, nag_interval_minutes (null = без напоминаний), **next_fire_at** — предвычисленный момент следующего срабатывания, ключ планировщика.
- `occurrence` — event_id, fired_at, status (OPEN/DONE/SUPERSEDED), **next_reminder_at** (сюда же пишет «Отложить»), done_at, telegram_message_id (для редактирования сообщения по кнопкам).

Схемой владеет Flyway; Hibernate работает в режиме `validate`.

## Планировщик

Один цикл раз в ~30 секунд, два запроса:

1. `event`: status = ACTIVE и next_fire_at <= now → создать occurrence, отправить сообщение,
   открытое старое occurrence пометить SUPERSEDED, пересчитать next_fire_at.
2. `occurrence`: status = OPEN и next_reminder_at <= now → отправить напоминание,
   сдвинуть next_reminder_at на nag-интервал (с учётом рабочих часов).

## Команды и UI бота

- `/start` — онбординг: таймзона, рабочие часы (дефолт с кнопкой «изменить»).
- `/new` — пошаговый визард: название → первое срабатывание (ЧЧ:ММ или ДД.ММ ЧЧ:ММ) → периодичность срабатываний (пресеты: однократно / ежедневно / каждые N минут / каждые N часов; «еженедельно» — v2) → периодичность напоминаний (пресеты) → итоговое резюме (отдельного шага подтверждения нет).
- `/manage` — активные события с кнопками: ⏸ пауза / ▶ продолжить / ✏️ изменить / 🗑 удалить. Завершение серии живёт на самих уведомлениях (🏁 завершить серию).
  - ✏️ изменить открывает меню полей: название / периодичность / время / напоминания. Правится по одному полю; «какое событие правим» хранится в `app_user.editing_event_id` (текстовые и календарные шаги не несут id в callback). Смена типа+параметра расписания атомарна — тип применяется вместе с параметром на финальном шаге. `next_fire_at` пересчитывается только для ACTIVE (у PAUSED — при возобновлении).
- `/finished` — read-only таблица завершённых событий (`status = FINISHED`), новые сверху, со столбцом даты завершения (`event.finished_at`).
- `/clear` — очистить переписку с ботом (с подтверждением). **Ограничение Telegram:** у Bot API нет «очистить историю», а свои/входящие сообщения бот удаляет только моложе 48 ч. Реализация — best-effort: идём по `message_id` вниз от сообщения-подтверждения (id последовательны в пределах чата, потолок `CLEAR_SCAN_LIMIT`) и удаляем каждое; что старше 48 ч, просто не удалится. Полный вайп доступен только самому пользователю (меню чата → «Очистить историю»); в итоговой сводке об этом сказано. События и напоминания не затрагиваются.
- `/settings` — таймзона, рабочие часы.
- Сообщение-уведомление: **✅ Готово** | **⏰ Отложить** (10 мин / 1 час / завтра) | для регулярных — **🏁 Завершить серию**.

## Гигиена чата

Чтобы лента не засорялась, на каждое срабатывание в чате живёт **ровно одно** сообщение:

- **Напоминание** удаляет предыдущее сообщение срабатывания и шлёт новое (не `editMessage` — правка на месте не даёт нового пуша, а нам нужно снова уведомить). Удаление best-effort: Telegram запрещает боту удалять свои сообщения старше 48 ч, поэтому при неудаче откатываемся на снятие кнопок у застрявшего сообщения.
- **Закрытие** срабатывания (Готово / Завершить серию / вытеснение по правилу «долг не копится» / пауза) не удаляет сообщение, а редактирует его в **компактный след** без кнопок: `✅ <название> — ЧЧ:ММ`, `🏁 … — серия завершена`, `⏭ … — заменено новым`, `⏸ … — на паузе`. История видна, шум убран.
- Сообщения `/list` этим не затрагиваются — там кнопки по-прежнему просто снимаются.
- **Команды пользователя** (`/list`, `/new`, `/help`, …) удаляются сразу после обработки — сам текст команды в ленте не нужен, ответ бота его замещает.

## Конфигурация и секреты

- Токен бота — **только из переменной окружения** `TELEGRAM_BOT_TOKEN` (маппится в `notifier.telegram.bot-token`). В репозитории токена нет; локально — файл `.env` (git-ignored, шаблон в `.env.example`).
- Параметры БД — env-переменные `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` с дефолтами под локальный `docker-compose.yml`.
- Локальная БД: `docker compose up -d` (PostgreSQL 17, порт 5432).
- Тесты: Testcontainers с реальным PostgreSQL — требуется запущенный Docker Desktop.
- Приложение контейнеризовано: multi-stage `Dockerfile` + сервис `app` в `docker-compose.yml` (`docker compose up -d --build`); токен подаётся через `env_file: .env`.
- CI/CD: `.github/workflows/deploy.yml` (push в master → тесты → образ в GHCR → деплой по SSH на VPS через `docker-compose.prod.yml`). Подробности и разовая настройка — `docs/DEPLOY.md`.
